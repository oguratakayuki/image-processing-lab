# ドキュメント運用ガイド

このリポジトリの`FEATURES.md`・`docs/`配下のドキュメントを書く・編集する際に**常に従うべきルール**。Claude Codeがこのリポジトリで作業する際は、指示がなくても本ガイドに従うこと（`CLAUDE.md`から参照されている）。

## ディレクトリ構成

```
FEATURES.md                          # トップページ（全体の索引）
docs/
├── DOCUMENTATION_GUIDE.md           # 本ファイル
├── features/                        # 機能ごとの解説（グループ単位）
│   ├── 1-color/
│   │   ├── README.md                # グループ概要ページ
│   │   ├── 1-1-grayscale.md         # 項目詳細ページ
│   │   ├── 1-2-brightness-contrast.md
│   │   ├── 1-3-histogram.md
│   │   ├── 1-3-histogram-ravel.md   # 補足資料（特定の行・式の深掘り）
│   │   ├── 1-4-threshold.md
│   │   └── assets/                  # 図版（SVGなど）
│   │       └── 1-1-rgb-projection.svg
│   ├── 2-convolution/
│   │   ├── README.md
│   │   ├── 2-1-convolution.md
│   │   ├── 2-1-convolution-fh-notation.md
│   │   ├── 2-2-kernel-presets.md
│   │   └── 2-3-opencv-comparison.md
│   ├── 3-edge/README.md             # 詳細ページ未整備なら早見表だけのREADMEのみ
│   └── 4-morphology/README.md
└── math/                             # トピックを横断する「コード⇔数式」対応資料
    ├── README.md                     # 索引
    ├── mean-kernel.md
    ├── gaussian-kernel.md
    └── gaussian-2d-function.md       # 1つの項をさらに深掘りした資料
```

**グループ番号**は、実装済みのWebページ（`/lab/*`）に対応する連番（1=色調整, 2=畳み込み, 3=エッジ検出, 4=二値画像処理, ...）。元の9トピックのカリキュラム番号とは別の、この`docs/features/`専用の通し番号。

## 採番ルール

- グループ：`N`（例：`2`）
- グループ内の項目：`N-M`（例：`2-1`, `2-3`）。会話中で「2-1について解説して」のように**番号で参照するためのキー**として機能させる
- 早見表（`FEATURES.md`・各グループの`README.md`）で、主機能ではなく補助的な機能は「（補助）」と付記する（例：「カーネルプリセット（補助）」）が、番号自体は通常の項目と同様に振る

## ファイル命名規則

| 種類 | 命名パターン | 配置場所 |
|---|---|---|
| グループ概要 | `README.md` | `docs/features/N-slug/` 直下（GitHub上でフォルダを開くと自動表示されるため必ず`README.md`にする） |
| 項目詳細ページ | `N-M-slug.md` | `docs/features/N-slug/` |
| 補足資料（特定の行・式の深掘り） | `N-M-slug-補足内容.md` | 親ページと同じフォルダ |
| 横断的な数式⇔コード対応資料 | `funcname.md` （番号プレフィックスなし） | `docs/math/` |
| 図版・画像 | 元の形式のまま（SVG推奨、HTMLは不可） | `docs/features/N-slug/assets/` |

## 項目詳細ページ（`N-M-*.md`）の構成

1. `# N-M. タイトル`
2. パンくず：`[← N. グループ名へ戻る](README.md)`
3. ページャー：`｜　[N-1](...) · **N-M** · [N-(M+1)](...)`（太字＝現在地）
4. 情報テーブル：

   ```
   | | |
   |---|---|
   | 学習テーマ | ... |
   | 実装ファイル | [`path/to/file.py`](GitHubのblob URL) |
   | 関数 | `func_name()` |
   | テスト | [`path/to/test.py`](GitHubのblob URL) |
   ```

5. `## 概念` — 直感的な説明（1〜3文程度）
6. `## 数学的背景` — 数式（**書き方のルールは下記「数式の書き方」を参照**）
7. `## 実装コード` — 実際のソースコードをそのまま引用（docstringは省き、解説は次のセクションで行う）
8. `### 解説` — コードを1行ずつ、数式との対応を示しながら説明する番号付きリスト
9. （必要に応じて）会話で深掘りした内容を追加のサブセクションとして挿入
10. `## 補足資料` または文中の`→ ...は[補足資料](リンク)を参照` — 関連する深掘りページ・図版へのリンク
11. `## 関連` — 関連する他の項目へのリンク（前後のトピックとのつながり）
12. `---`
13. ナビゲーション：`前へ: [← 前のページ]　｜　次へ: [次のページ →]`
    - 最初の項目（1-1）は「前へ: なし（最初の項目）」
    - グループを跨ぐ場合もそのまま次グループの最初の項目へリンクする（グループのREADMEを経由しない）
    - 次グループの詳細ページがまだ無い場合は、グループのREADMEにリンクしつつ「（詳細ページは未整備）」と明記する

## グループ概要ページ（`README.md`）の構成

1. `# N. グループ名（\`/lab/xxx\`）`
2. `[← 機能一覧トップへ戻る](../../../FEATURES.md)`
3. 導入文（このグループで何を学ぶか、前のグループとのつながり）
4. `## このグループの流れ` — `| 番号 | 処理 | 一言で言うと |`のテーブル
5. 各項目がどうつながっているかの説明文
6. `## 数学的な見どころ` — このグループを貫く数学的テーマの箇条書き（まだ存在しないグループへの前方参照は、リンクを貼らずプレーンテキストで触れる程度に留める）
7. `## 実装` — APIルーター・Webページのファイルパス（補助的な配線情報）

## 補足資料ページの作り方

会話中の説明が分かりやすく、残しておく価値があると判断したら、その場で補足資料化する。

- ファイル名：親ページの番号を引き継ぎ、内容が分かるサフィックスを付ける（例：`1-3-histogram-ravel.md`）
- 構成：タイトル→親ページへの戻りリンク→説明本文（会話で使った説明・構成をそのまま踏襲してよい）→`## 関連`
- 親ページ側には、**該当する行・数式のすぐ近くに**リンクを挿入する（ページ末尾にまとめて置かない）。リンクの文言は「（補足資料）」または「→ ...は[補足資料](リンク)を参照」を使う

## `docs/math/`（横断的な数式⇔コード対応資料）の作り方

**目的はコンセプト説明ではなく、「このコードの各行が数式のどの部分に対応するか」を1対1で示すこと**。複数のグループ・トピックから参照されうる内容はここに置く（特定の`N-M`ページの下には置かない）。

- `docs/math/README.md`に索引テーブル（`| 資料 | 対象 | 参照元 |`）を必ず更新する
- 各資料の構成：`# funcname：コード⇔数式対応` → 戻りリンク → `## コード`（実コード） → `## 数式` → `## コードと数式の対応`（1行またはブロック単位で「何をしているか／なぜ必要か」を解説） → `## 具体的な計算例`（具体的な数値での計算、できる限り既存のpytestのテストケースと一致させる）
- 1つの項（式の一部）がさらに深掘りを要するほど複雑な場合、`funcname-subtopic.md`のように分割し、元の資料からは要約1文＋リンクに留める

## リンクの付け方

- **「実装ファイル」は必ずGitHubの実ファイルへのリンク**：`https://github.com/oguratakayuki/image-processing-lab/blob/main/<path>`
- **ドキュメント間の相互リンクは相対パス**を使う（絶対URLにしない）。絶対URLはソースコードファイルへのリンクにのみ使う
- **存在しないページには絶対にリンクを貼らない**。まだ無いトピックに触れる場合はリンクなしのプレーンテキストで言及するに留める
- 補足資料へのリンクには「補足資料」という語を一貫して使う

## 数式の書き方（最重要・既知の落とし穴）

**インラインLaTeX（`$...$`・`$$...$$`）は使用しない。** GitHub上での実際のレンダリングを検証した結果、以下の理由で不安定であることが判明したため。

- 生の`<` `>`文字を含む数式は、MarkdownパーサーがHTMLタグの開始と誤認識してレンダリングが壊れる
- アンダースコアによる添字（`\sum_v`など）が、Markdownの斜体記法（`_text_`）と衝突してレンダリングが壊れる
- 同じページ内でも、レンダリングされる数式とされない数式が混在する不安定な挙動が確認された

**代わりに以下を使う：**

- 短い式：バッククォートで囲んだプレーンテキスト（例：`` `f(0)=0` ``、`` `g(x)=alpha*x+beta` ``）
- 複数行の式・`<` `>`を含む式：フェンス付きコードブロック（```` ``` ````）。コードブロックの中身はGitHubが絶対にHTMLとして解釈しないため最も安全
- 数学記号はUnicode文字をそのまま使ってよい（`Σ`, `√`, `²`, `·`, `∫`, `∂`, `∇`, `π`, `α`, `β`, `σ`, `τ`など）。LaTeXコマンド（`\sum`など）としてではなく、ただの文字として使う

GitHub上の実際の表示を確認する際は、思い込みで判断せず、実際にGitHubのページを見る（Playwrightでスクリーンショット、または`WebFetch`、できればユーザー自身のログイン済みブラウザでの確認）。ヘッドレスブラウザでの自動チェックも完全には信頼できないことが分かっているため、疑わしい場合はユーザーに実際の見え方を確認してもらう。

## 数値・コード例の検証

- ドキュメントに載せる数値計算例は、**必ず実際に計算（Bash経由でpython3を実行するなど）してから記載する**。手計算や記憶に頼らない（過去に手計算のミスで修正が発生したため）
- 可能な限り、既存のpytestのテストケース（`engine/tests/`配下）と同じ入力・期待値を使う。実装の正しさとドキュメントの正しさが二重に裏付けられる
- 図版（SVGなど）を追加する際は、Playwrightでスクリーンショットを撮って実際に意図通り表示されるか確認してから配置する

## commitメッセージの書き方（技術的な注意）

このmacOS環境のシェルで、`git commit -m "$(cat <<'EOF' ... EOF)"`というヒアドキュメント形式は、本文に特定の文字（日本語の記号など）が含まれると`unexpected EOF`エラーで失敗することが繰り返し確認されている。コミットメッセージはスクラッチ領域に一時ファイルとして書き出し、`git commit -F <一時ファイル>`を使うこと。
