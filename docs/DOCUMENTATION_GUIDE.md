# ドキュメント運用ガイド

このリポジトリの`FEATURES.md`・`docs/`配下のドキュメントを書く・編集する際に**常に従うべきルール**。Claude Codeがこのリポジトリで作業する際は、指示がなくても本ガイドに従うこと（`CLAUDE.md`から参照されている）。

```

│   │   ├── 1-3-histogram.md

│   │   ├── 1-4-threshold.md

**グループ番号**は、実装済みのWebページ（`/lab/*`）に対応する連番（1=色調整, 2=畳み込み, 3=エッジ検出, 4=二値画像処理, ...）。元の9トピックのカリキュラム番号とは別の、この`docs/features/`専用の通し番号。

## 採番ルール

- グループ：`N`（例：`2`）
- グループ内の項目：`N-M`（例：`2-1`, `2-3`）。会話中で「2-1について解説して」のように**番号で参照するためのキー**として機能させる
- 早見表（`FEATURES.md`・各グループの`README.md`）で、主機能ではなく補助的な機能は「（補助）」と付記する（例：「カーネルプリセット（補助）」）が、番号自体は通常の項目と同様に振る

## ファイル命名規則

| 種類 | 命名パターン | 配置場所 |
|---|---|---|
| グループ概要 | `README.md` | `docs/features/N-slug/` 直下（GitHub上でフォルダを開くと自動表示されるため必ず`README.md`にする） |
| 項目詳細ページ | `N-M-slug.md` | `docs/features/N-slug/` |
| 補足資料（特定の行・式の深掘り） | `N-M-slug-補足内容.md` | 親ページと同じフォルダ |
| 横断的な数式⇔コード対応資料 | `funcname.md` （番号プレフィックスなし） | `docs/math/` |
| 図版・画像 | 元の形式のまま（SVG推奨、HTMLは不可） | `docs/features/N-slug/assets/` |

## 項目詳細ページ（`N-M-*.md`）の構成

1. `# N-M. タイトル`
2. パンくず：`[← N. グループ名へ戻る](README.md)`
3. ページャー：`｜　[N-1](...) · **N-M** · [N-(M+1)](...)`（太字＝現在地）
4. 情報テーブル：

   ```
   | | |
   |---|---|
   | 学習テーマ | ... |
   | 実装ファイル | [`path/to/file.py`](GitHubのblob URL) |
   | 関数 | `func_name()` |
   | テスト | [`path/to/test.py`](GitHubのblob URL) |
   ```

5. `## 超ざっくり言うと` — 専門用語を使わない1〜2文の平易な言い換え。「結局これは何をする処理か」を一番最初に掴めるようにする
6. `## 概念` — 直感的な説明（1〜3文程度）
7. `## 主な用途` — 実務・一般的な画像処理でどんな場面で使われるか（箇条書き）。このプロジェクトの実装固有の話ではなく、一般論としての使いどころを書く
8. `## 数学的背景` — 以下の3段構成にする（**数式の書き方のルールは下記「数式の書き方」を参照**）
   - `### 要件` — 何を達成したいか（ゴール）
   - `### やるべきこと` — ゴールを満たすために何を判定・計算すればよいか、その数式
   - `### コードにすると` — その数式が実装のどの処理に対応するか、1〜2文で後述の実装コードへ橋渡しする
9. `## 実装コード` — 実際のソースコードをそのまま引用する。docstring全体（数学的背景・前提条件など）は`## 概念`・`## 数学的背景`側で既に説明しているため省くが、**引数・返却値の説明だけは`#`コメントとして関数内に残す**（詳しい解説は次のセクションで行う）
10. `### 解説` — コードを1行ずつ、数式との対応を示しながら説明する番号付きリスト
11. （必要に応じて）会話で深掘りした内容を追加のサブセクションとして挿入
12. `## 補足資料` または文中の`→ ...は[補足資料](リンク)を参照` — 関連する深掘りページ・図版へのリンク
13. `## 関連` — 関連する他の項目へのリンク（前後のトピックとのつながり）
14. `---`
15. ナビゲーション：`前へ: [← 前のページ]　｜　次へ: [次のページ →]`
    - 最初の項目（1-1）は「前へ: なし（最初の項目）」
    - グループを跨ぐ場合もそのまま次グループの最初の項目へリンクする（グループのREADMEを経由しない）
    - 次グループの詳細ページがまだ無い場合は、グループのREADMEにリンクしつつ「（詳細ページは未整備）」と明記する

## グループ概要ページ（`README.md`）の構成

1. `# N. グループ名（\`/lab/xxx\`）`
2. `[← 機能一覧トップへ戻る](../../../FEATURES.md)`
3. 導入文（このグループで何を学ぶか、前のグループとのつながり）
4. `## このグループの流れ` — `| 番号 | 処理 | 一言で言うと |`のテーブル
5. 各項目がどうつながっているかの説明文
6. `## 数学的な見どころ` — このグループを貫く数学的テーマの箇条書き（まだ存在しないグループへの前方参照は、リンクを貼らずプレーンテキストで触れる程度に留める）
7. `## 実装` — APIルーター・Webページのファイルパス（補助的な配線情報）

## 補足資料ページの作り方

会話中の説明が分かりやすく、残しておく価値があると判断したら、その場で補足資料化する。

- ファイル名：親ページの番号を引き継ぎ、内容が分かるサフィックスを付ける（例：`1-3-histogram-ravel.md`）
- 構成：タイトル→親ページへの戻りリンク→説明本文（会話で使った説明・構成をそのまま踏襲してよい）→`## 関連`
- 親ページ側には、**該当する行・数式のすぐ近くに**リンクを挿入する（ページ末尾にまとめて置かない）。リンクの文言は「（補足資料）」または「→ ...は[補足資料](リンク)を参照」を使う

## `docs/math/`（横断的な数式⇔コード対応資料）の作り方

**目的はコンセプト説明ではなく、「このコードの各行が数式のどの部分に対応するか」を1対1で示すこと**。複数のグループ・トピックから参照されうる内容はここに置く（特定の`N-M`ページの下には置かない）。

- `docs/math/README.md`に索引テーブル（`| 資料 | 対象 | 参照元 |`）を必ず更新する
- 各資料の構成：`# funcname：コード⇔数式対応` → 戻りリンク → `## コード`（実コード） → `## 数式` → `## コードと数式の対応`（1行またはブロック単位で「何をしているか／なぜ必要か」を解説） → `## 具体的な計算例`（具体的な数値での計算、できる限り既存のpytestのテストケースと一致させる）
- 1つの項（式の一部）がさらに深掘りを要するほど複雑な場合、`funcname-subtopic.md`のように分割し、元の資料からは要約1文＋リンクに留める

## `docs/qa/README.md`（Q&A一覧）の作り方

会話中にユーザーが疑問に思って質問した内容（「〜ということで合っていますか？」「〜とは何ですか？」など）とその回答を蓄積していく、随時追加型の一覧ページ。

- 1ファイル（`docs/qa/README.md`）にテーブル形式（`| # | 質問 | 回答 | 詳細 |`）で追記していく。番号は追加した順の連番で、既存の番号は変更しない
- **質問**：ユーザーの発言をほぼそのまま（口語をやや整える程度）載せる
- **回答**：ここで完結する簡潔な1〜3文。詳しい計算過程・derivationは書かない
- **詳細**：回答の元になった説明が載っている既存ページへのリンク（新規ページは作らない。既存の`N-M`詳細ページ・補足資料・`docs/math/`のいずれかに必ず紐付ける）
- アンカー付きリンクは、既に動作確認済みのものがあればそれを再利用してよいが、新しく追加した見出しへのアンカーは**推測で貼らない**（上記「数式の書き方」の下にある注意と同じ理由）。確認が取れるまではページ単位のリンクに留める

## リンクの付け方

- **「実装ファイル」は必ずGitHubの実ファイルへのリンク**：`https://github.com/oguratakayuki/image-processing-lab/blob/main/<path>`
- **ドキュメント間の相互リンクは相対パス**を使う（絶対URLにしない）。絶対URLはソースコードファイルへのリンクにのみ使う
- **存在しないページには絶対にリンクを貼らない**。まだ無いトピックに触れる場合はリンクなしのプレーンテキストで言及するに留める
- 補足資料へのリンクには「補足資料」という語を一貫して使う

## 数式の書き方（最重要・既知の落とし穴）— LaTeX数式マニュアル

GitHub上での実際のレンダリングを繰り返し検証した結果に基づく、確定版のルール。新しく数式を書く・直す際は**必ずこのセクションを参照する**。

### 使ってよいもの・使ってはいけないもの（早見表）

| 書き方 | 可否 | 備考 |
|---|---|---|
| インライン`$...$` | ❌ 禁止 | 下記「インラインが壊れる理由」を参照。常にブロック`$$`かバッククォート/コードブロックで代替する |
| ブロック`$$...$$`（1行で完結する数式） | ✅ 使ってよい | 添字・Σ・積分・指数・ギリシャ文字を含んでいても良い。複数の式変形を書く場合は式ごとに別々の`$$...$$`ブロックに分ける（1つの`$$`に複数行を詰め込まない） |
| `\begin{bmatrix}`等の複数行環境 | ❌ 禁止 | 改行（`\\`）が無視されて1行に潰れる（2026-10-09確認）。行列はUnicode括弧のプレーンテキストを使う（後述） |
| `\,` `\;` `\quad`などの**スペーシングコマンド** | ❌ 禁止 | `\,`は余白ではなく**リテラルのカンマ`,`として表示される**という重大な不具合を確認済み（2026-10-20、`\int f(\tau) \, h(x-\tau)`が`∫f(τ), h(x-τ)`と表示された）。`\;`・`\quad`は未検証だが、同じレンダラーの不具合に当たる可能性があるため使わない。項の間の余白が欲しい場合は、何も書かずそのまま隣接させる（`$$`内の空白はレンダラーが自動で適切な間隔を入れる） |
| `<` `>`を含む数式 | ❌ `$$`でも禁止 | MarkdownパーサーがHTMLタグの開始と誤認識する。フェンス付きコードブロック（```` ``` ````）を使う |

### インラインLaTeX`$...$`が壊れる理由（既知の問題）

- 生の`<` `>`文字を含む数式は、MarkdownパーサーがHTMLタグの開始と誤認識してレンダリングが壊れる
- アンダースコアによる添字（`\sum_v`など）が、Markdownの斜体記法（`_text_`）と衝突してレンダリングが壊れる
- 同じページ内でも、レンダリングされる数式とされない数式が混在する不安定な挙動が確認された

### ブロック数式`$$...$$`について分かっていること

- **添字・Σ・積分・指数を含む、1行で完結する数式は正しくレンダリングされる**（2026-10-18確認：`X_k = \sum_{n=0}^{N-1} x_n \cdot e^{-2\pi i k n / N}`、`e^{i\theta} = \cos(\theta) + i \sin(\theta)`、2026-10-20確認：`(f * h)(x) = \int f(\tau) h(x - \tau) d\tau`、`(I * K)(x, y) = \sum_{i=-k}^{k} \sum_{j=-k}^{k} K(i, j) \cdot I(x - i, y - j)`など）。アンダースコア添字がインライン`$...$`と違って`$$`ブロック内では崩れないことも確認済み
- **`\begin{bmatrix}`等の複数行環境は壊れる**（改行`\\`が無視されて1行に潰れる）
- **`\,`は余白ではなくカンマとして表示される**（2026-10-20確認）。他のスペーシングコマンド（`\;`、`\quad`など）も未検証のため使わないこと。項の間の余白はレンダラーの自動調整に任せ、明示的なスペーシングコマンドは一切使わない
- 日本語の説明文を数式と同じ行・同じ`$$`ブロックに混ぜない（例：`F[I*K]=F[I]*F[K]   (Fはフーリエ変換)`のような書き方はしない）。数式は`$$`ブロック単体にし、説明は`$$`ブロックの外（前後の地の文やカッコ書き）に出す

### 使い分けの目安

- 短い式：バッククォートで囲んだプレーンテキスト（例：`` `f(0)=0` ``、`` `g(x)=alpha*x+beta` ``）
- 添字・Σ・積分・指数などを含む、1行で完結する数式：`$$...$$`ブロック数式を使う
- `<` `>`を含む式：フェンス付きコードブロック（```` ``` ````）。コードブロックの中身はGitHubが絶対にHTMLとして解釈しないため最も安全
- 複数行にまたがる式（行列など）：フェンス付きコードブロック。数学記号はUnicode文字をそのまま使ってよい（`Σ`, `√`, `²`, `·`, `∫`, `∂`, `∇`, `π`, `α`, `β`, `σ`, `τ`など）
- **行列**：`\begin{bmatrix}`は使わず、フェンス付きコードブロック内でUnicodeの複数行対応括弧（`⎡⎤`＝上段、`⎢⎥`＝中段、`⎣⎦`＝下段）を使うと、等幅フォント上で綺麗に揃った行列として表示できる（2026-10-09にGitHub上で実例確認済み）。例：

  ```
  ⎡x'⎤   ⎡sx   0⎤ ⎡x⎤
  ⎢  ⎥ = ⎢      ⎥ ⎢ ⎥
  ⎣y'⎦   ⎣ 0  sy⎦ ⎣y⎦
  ```

### 検証の徹底（必須）

GitHub上の実際の表示を確認する際は、思い込みで判断せず、実際にGitHubのページを見る（Playwrightでスクリーンショット、または`WebFetch`、できればユーザー自身のログイン済みブラウザでの確認）。ヘッドレスブラウザでの自動チェックも完全には信頼できないことが分かっているため、疑わしい場合はユーザーに実際の見え方を確認してもらう。**`$$...$$`ブロック数式を新しく書く・編集する場合は、上記の早見表で確認済みのパターン（添字・Σ・積分・指数のみ、スペーシングコマンドなし）に沿っているか毎回確認し、少しでも新しい要素（未検証のコマンド・環境）を含む場合は、commit・push後に必ずGitHub上の実際の表示を確認してから確定させる。**

## 数値・コード例の検証

- ドキュメントに載せる数値計算例は、**必ず実際に計算（Bash経由でpython3を実行するなど）してから記載する**。手計算や記憶に頼らない（過去に手計算のミスで修正が発生したため）
- 可能な限り、既存のpytestのテストケース（`engine/tests/`配下）と同じ入力・期待値を使う。実装の正しさとドキュメントの正しさが二重に裏付けられる
- 図版（SVGなど）を追加する際は、Playwrightでスクリーンショットを撮って実際に意図通り表示されるか確認してから配置する

## commitメッセージの書き方（技術的な注意）

このmacOS環境のシェルで、`git commit -m "$(cat <<'EOF' ... EOF)"`というヒアドキュメント形式は、本文に特定の文字（日本語の記号など）が含まれると`unexpected EOF`エラーで失敗することが繰り返し確認されている。コミットメッセージはスクラッチ領域に一時ファイルとして書き出し、`git commit -F <一時ファイル>`を使うこと。
